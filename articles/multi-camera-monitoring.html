Designing a multi-camera monitoring pipeline

When an application must show multiple live camera feeds and run computer-vision inference, treating everything as one loop makes debugging and capacity planning harder. Separate responsibilities first, then measure the system under its actual network conditions.

Example flow
RTSP camera
Video sourceFrame capture
Reconnect / latest frameInference worker
Model workloadAPI + dashboard
Results / stream

Separate three workloads

Capture keeps a usable frame available and recovers from camera or network interruptions. It should expose stale-frame and reconnect conditions instead of hiding them.

Inference has a different budget. Model size, image resolution, batching and accelerator availability influence throughput and latency. The displayed frame rate is not the same as the rate at which unique frames are analysed.

Browser streaming delivers a view of the feed; it should not become the only place frames are acquired or force model processing to run at a viewer's pace.

Plan for network and browser constraints

RTSP quality depends on camera configuration, network path, packet loss and reconnect behavior. Remote access paths such as VPN relays can affect latency. Browsers also impose connection and resource limits, so test the target browser, protocol and number of simultaneous feeds rather than assuming a single-feed demo scales unchanged.

Measure what matters

  • Capture uptime, reconnect count and time since the last good frame.
  • Inference throughput, queue depth and end-to-end detection latency.
  • Stream startup time, browser rendering stability and bandwidth.
  • CPU/GPU utilization and memory at the intended camera count.
Reporting rule: publish FPS, detection accuracy or capacity numbers only after recording camera count, frame size, model version, hardware, network conditions and the measurement method.
